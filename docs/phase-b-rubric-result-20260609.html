Phase B HealthBench rubric — Gemma 4 E4B ±RAG result

MAM-AI v0.2 · open-ended rubric track · gpt-oss-120b @ reasoning_effort=medium judge · 38,308 criterion calls · 2026-06-09

Headline. Across all three HealthBench subsets, retrieval-augmented generation (+RAG) produces a slightly worse `weighted_met` score than the no-RAG baseline. Direction is consistent across all subsets; magnitudes range from −0.3 pp (hard) to −2.0 pp (consensus) of the maximum possible score. RAG does not improve the rubric-track headline; the small effect goes against the v0.2 deployment hypothesis.

Caveat. The pinned judge (gpt-oss-120b @ medium) has a documented per-criterion bias profile — see Phase A judge calibration. Direction of the RAG effect is robust to that bias; magnitude is approximately the right size relative to it. No bootstrap CIs computed here yet — the 2 pp consensus delta is the largest single-arm signal and likely above noise, but smaller deltas may not be.

Method

Phase B scored Gemma 4 E4B's existing HealthBench-track responses (both ±RAG arms, generated on the cluster in May) with the pinned judge identified by Phase A. Six result JSONs were rescored in-place via end_to_end_eval/rescore_rubric.py on the EPFL RunAI cluster (cluster/rescore_rubric.sh on a single H200): vLLM serves openai/gpt-oss-120b at reasoning_effort=medium, the production scorer calls it via the OpenAI client at the local vLLM endpoint, and each (response, criterion) pair gets a binary met verdict written back into the result JSON.

What weighted_met measures

Each HealthBench rubric criterion carries an integer points value — positive for "the response should…" criteria, negative for "the response should not…" penalties. The judge labels each criterion met=True/False. For each row:

weighted_met = (sum of points where met=True) / (sum of max(points, 0))

+1.0
The response met every positive criterion and triggered no penalty criterion — the ceiling.
+0.5
About half the positive points captured, no penalties triggered (or equivalently: most positives plus a few penalties).
0.0
Either: nothing matched, or — more commonly in this dataset — what the model got right is offset by penalty criteria it also triggered.
Negative
The model triggered more penalty value than the positive value it earned. Common when penalty criteria are heavy ("should not recommend X dangerous thing") and the model violates them.

Note on denominator. Only positive criteria count toward the denominator, so the scale is "fraction of achievable positive credit, net of penalties." A score near zero means achievements and penalties roughly cancel — not that the model produced nothing.

The pattern is unambiguous in direction — all three deltas are negative, meaning RAG-on lowers `weighted_met` on every subset — but the magnitudes are small in absolute terms:

  • consensus (−2.0 pp) is the largest delta and the one above plausible noise. RAG materially trades off some performance on these clearer rubric items.
  • oss_eval (−0.5 pp) is a small but consistent shift. Both arms are essentially "break-even" on this subset (positives nearly cancel penalties), and RAG pushes that balance slightly toward net-negative.
  • hard (−0.3 pp) is within noise range; gpt-oss-120b's known per-criterion under-rating on borderline NOT-MET rows makes us treat very small magnitudes here with caution.

  1. Completeness is the only axis with a negative mean in both arms (~−0.20).   2. RAG's biggest negative impacts hit communication_quality (−3.4 pp) and instruction_following (−3.2 pp), not the axes one would expect retrieval to affect (accuracy / context_awareness). This is consistent with retrieval contexts injecting extra material that gets in the way of clean answers and dilutes the model's adherence to the asked-for form.

How to read these numbers, concretely

The weighted_met scale feels small when reading the consensus row's 0.512 vs 0.492. A useful translation: that 2.0 pp delta means RAG-on on average loses Gemma 2% of the maximum possible positive credit per response, sustained over 872 prompts. For a deployment that ships ~hundreds of conversations per day, that's a steady downward pressure on the headline rubric metric — small per-row but cumulatively visible.

Caveats — judge calibration

The pinned judge has documented bias relative to physician ground truth (see Phase A calibration report). The key facts for interpreting Phase B results:

  • gpt-oss-120b's overall judge met-rate is 73.2%, just −3.8 pp below the physician baseline of 77% (the closest calibration of any judge tested across 5 candidates + 2 trivial baselines).
  • On the NOT-MET-row subset (concordant cases where physicians agreed a criterion was NOT met), the judge agrees only 67.9% of the time vs the 77.6% human-human ceiling — a real ~10 pp under-detection of failures. This is the disclosure to surface in the v0.2 methods section.
  • Effect on Phase B numbers: the absolute weighted_met values shown here are likely slightly understated vs what physicians would produce (since the judge under-detects some failures the model genuinely satisfied). But the ±RAG comparison is robust — both arms are judged by the same judge with the same bias, so the Δ values cancel that bias out and reflect a real difference in Gemma's outputs.

So: if a reviewer pushes back on absolute scores, the answer is "see Phase A — judge under-rates met by ~3.8 pp on average, so absolute scores are lower bounds." If a reviewer pushes back on the ±RAG comparison, the answer is "judge bias cancels in the Δ; the direction is robust."

What this changes for v0.2

  • The RAG arm should not be presented as a quality improvement on the rubric track. The honest framing is: "retrieval brings in additional context but does not improve and slightly hurts HealthBench-rubric headline performance on the OBGYN scope tested."
  • Completeness emerges as the priority axis for future model/prompt iteration — it's where the model is genuinely failing, RAG-neutral.
  • Per-iteration budget impact (from the budget doc): future RAG-arm-only rescore iterations cost ~$0 (cluster), so the cost story for retrying retrieval improvements is unchanged. But each iteration now starts from a baseline where RAG slightly hurts; improvements will need to make up that gap before they're a net win.
