Is the EmbeddingGemma retrieval score thresholdable? (EG × Gemma 3n, kenya)

2026-06-18 · config-v0.2.0 · no reranker · kenya (312 queries; 300 with end-to-end recall). Tests whether a cosine-similarity threshold can drive a confidence / abstention gate — the idea R1 shelved for Gecko cosine, re-asked for EmbeddingGemma. R1's bar: chunk-level AUC ≥ 0.80.

Verdict: not thresholdable for a usable gate. EmbeddingGemma's cosine score carries a real but modest relevance signal (chunk AUC 0.72, 95% CI [0.69, 0.75] — below the 0.80 bar) yet, against a ~20% relevant base rate, no cutoff yields usable precision (≤0.41 even at the most selective). And it has no relationship to answer quality (answer AUC 0.50 = random). A cosine confidence gate would mostly mis-fire.

Pooled AUC = one global threshold over all (query,chunk) pairs (the relevant quantity for a single deployed gate); CI = cluster bootstrap resampling queries (300×). Per-query AUC = cosine's within-query ranking of relevant above irrelevant — weaker still (0.61), so the pooled number is the favourable framing. Both, and the whole CI, sit below 0.80.

There is a real signal: relevant chunks score higher than irrelevant ones (mean sim 0.565 vs 0.524; Cohen d ≈ 0.76, a medium–large effect). But a moderate AUC is not enough for a gate when only ~20% of retrieved chunks are relevant — at that base rate no cutoff cleanly splits them:

All three sit below the 0.80 viability bar — EmbeddingGemma fails R1's Stage-1 gate on every rule family, the same verdict R1 reached for Gecko. Two specifics:

  • The cross-query magnitude signals improve over Gecko but not enough. Chunk-level AUC 0.69 (vs Gecko 0.57) and bundle AUC 0.72 (vs 0.57) are clearly better — the better embedder does make scores somewhat more comparable corpus-wide — but both land in the 0.60–0.80 "no absolute cutoff" zone, short of the bar.
  • The within-bundle signal is actually worse (0.57 vs Gecko's 0.62), near chance. Inside a single top-3 bundle, EmbeddingGemma's cosine orders the genuinely-relevant chunk above the merely-on-topic one only 57% of the time — so relative-margin rules, which compare a bundle against itself, have essentially nothing to work with.

Caveats: R1's numbers are on the mamaretrieval audit queries (n=3,185); these are kenya (n=312), so the comparison is indicative, not strictly head-to-head — but the 0.80 bar is methodology-defined, not query-set-defined. The concordance is over only 281 co-bundle relevant/junk pairs (kenya has few mixed bundles), so it has a wide interval. (The 0.72 chunk AUC in Test A above pools the full top-20; this 0.69 is the top-3 bundle — same story, narrower population.)

Gated abstention — the direct test (the most promising rule family)

Bundle top-1 AUC (0.716 above) is the best of the three, so gated abstention deserves a direct test. But that statistic measures the wrong target — whether the bundle contains a relevant chunk. What gated abstention actually needs is: can the score tell us when RAG improves the answer, so we keep RAG on those queries and fall back to no-RAG on the rest? We have per-query recall both with RAG (EmbeddingGemma × 3n) and without (no-RAG × 3n), so we can test it head-on.

The opportunity is real — RAG helps some queries and hurts others, so a perfect gate would pay off:

Gated abstention is not viable on this score. There is a real +0.057 prize (oracle 0.354 vs always-RAG 0.297), but the cosine score is a chance-level (AUC 0.50) predictor of when RAG helps, so a score-gated policy captures none of it — its best operating point is just "keep RAG everywhere" (0.297). The reverse direction (keep RAG when score is low) is no better (0.285–0.293). A working gate would need a different signal — generator-side answer confidence or an explicit "does this context help" classifier — not retrieval similarity.

Test B — does the retrieval score predict answer quality?

The product-relevant question: could we abstain / fall back when retrieval is poor because the answer will be bad? Join per-query retrieval score (top-1, mean top-3 cosine) with per-query key-fact recall from the EmbeddingGemma × Gemma 3n end-to-end run (n=300 judged).

AUC ≈ 0.50 everywhere — pure noise (Pearson(score, recall) = −0.05). It holds on both the imbalanced cut (recall>0: 265 pos / 35 neg) and the balanced one (recall ≥ median: 153 / 147), so it is not an artefact of class imbalance. The retrieval score carries no information about whether the generated answer is good — consistent with the matrix finding that RAG is net-negative-to-null on this generator: retrieval quality and answer quality are decoupled.

Why & what it means

  • Confirms and extends R1. R1 shelved cosine thresholding for the deployed Gecko; this shows EmbeddingGemma — a clearly better retriever — is still under the 0.80 chunk-AUC bar (0.72) and is useless for answer-level gating (0.50). The retriever upgrade does not buy thresholdability.
  • No cosine abstention gate. Any threshold either keeps junk (high recall, ~0.26 precision) or discards most relevant chunks (low recall). There is no "confidence ≥ X ⇒ trustworthy" cutoff.
  • The lever, again, is downstream. Because retrieval score ⟂ answer quality, a useful abstention signal would have to come from the generator (answer-side confidence / self-consistency), not the retriever — the same conclusion as the generator × retriever matrix.
What could be thresholdable (not pursued): a fine-tuned cross-encoder score is more separable offline — mxbai-base-ft hit chunk AUC ≈ 0.86 on mamaretrieval (above the 0.80 bar). But (a) that gain didn't transfer to kenya retrieval, and (b) reranking added nothing end-to-end on EG × 3n (kenya 0.297 → 0.297/0.289), so a reranker-score gate would be thresholding a signal that doesn't track kenya answer quality. Reranking is out of scope here per decision to drop it.
