# Handoff — evaluating MAMAI on mamabench v0.2

*Filed 2026-05-15. Written for a fresh agent picking up the v0.2 evaluation in this repo. Read this first.*

---

## TL;DR

`mamabench v0.2` is published. This repo (`mamai-eval`) is the consumer. Three things differ from the v0.1 evaluation cycle:

1. **Data source moves from local TSV → HF dataset.** `datasets.load_dataset("nmrenyi/mamabench", "<config>", revision="v0.2")`.
2. **One new set type to score: `open_ended_rubric`** (HealthBench-style weighted-met). v0.1 had only `mcq` and `open_ended`.
3. **Open-ended scoring changes paradigm.** v0.1 used a single judge against the reference. v0.2 expects **key-fact recall via a 3-judge ensemble** — key facts are pre-extracted and inlined on each row.

Everything else (retrieval, latency, the cluster scripts, the `configs/config-vX.Y.Z` layout) carries over.

### Schema essentials (v0.4) for scoring

Every row has:
- `id`: `mamabench_v0.2_<source>_<source-row-id>`
- `set_type`: `"mcq" | "open_ended" | "open_ended_rubric"`
- `question`: string (single-turn) or `list[{role, content}]` (HealthBench multi-turn)
- `source`: `{dataset, id, answer?, metadata?}`

Set-type-conditional fields:

| set_type | Score against | Field shape |
|---|---|---|
| `mcq` | gold option | `choices: list[str]`, `answer: str`, `answer_index: int` |
| `open_ended` | reference + key_facts | `answer: str` (reference). Pre-extracted key facts live in `source.metadata.key_fact_extraction.key_facts: list[str]`. |
| `open_ended_rubric` | criteria list | `rubrics: list[{criterion_id, points}]`. Resolve `criterion_id` against `side_tables/healthbench_criteria.jsonl` for text + `level` + `axis`. |

## The eval matrix to fill

Per `mamai-quality-evaluation.md §4.1`:

| Model | No RAG | + RAG |
|---|---|---|
| **Gemma 4 E4B** (deployment target) | baseline | **deployed system** |
| MedGemma 4B / Meditron 70B | fine-tuning ablation | fine-tuning + RAG |
| Mid-size open (Llama 3 70B / Qwen 2.5 72B) | open-weights comparator | bigger-model-with-same-knowledge |
| Frontier (GPT-5 / Claude 4.7 / Gemini 2.5) | capability ceiling | overall ceiling |

**Don't try to fill the whole matrix at once.** Start with three cells: Gemma-no-RAG, Gemma-RAG, one frontier (e.g. Claude 4.7 no-RAG). Validate the runner + scorers end-to-end on those three before adding more models.

## Scoring per set_type — concrete recipe

### `mcq` (medmcqa, medqa_usmle, afrimedqa)

Existing `rescore_mcq.py` should largely transfer. Confirm:
- Reads `answer_index` (v0.4) instead of `correct_letter` (v0.1 TSV).
- Reports **accuracy** + **calibration** (Brier score, Expected Calibration Error). Calibration needs the model's logprobs over `choices`; if your runner only stores top-1 picks, calibration metrics will be unavailable until the runner is updated to capture logprobs.

### `open_ended` (kenya, afrimedqa_saq, whb)

Implements the recipe from `open_ended_evaluation_research.md §7`:

1. For each row, you have the question, the reference answer (`answer`), and **pre-extracted `key_facts: list[str]`** (already in `source.metadata.key_fact_extraction.key_facts` — no need to extract anything; that's already done at v0.2 build time).
2. Run a **3-judge ensemble** — `gpt-5`, `claude-opus-4-7`, `gemini-2.5-pro` (or whatever the current best-of-three is at eval time). Each judge gets: question, reference, key_facts, candidate response, and a structured prompt.
3. Each judge returns, per row:
   - **Per-key-fact verdict:** `present | partial | absent` + one-line justification.
   - **4 axis scores** on a 0–4 Likert: accuracy, completeness, safety (with `{safe, minor_concern, potentially_harmful, dangerous}` mapping), contextual appropriateness.
   - **Binary:** is the candidate ≥ as clinically useful as the reference?
   - **CoT rationale** above the JSON (variance reducer).
4. Aggregate: mean axis scores, majority-vote binary and per-key-fact verdicts.

**Headline metric:** **key-fact recall** = `(#present + 0.5 × #partial) / #key_facts` per row, averaged across the subset.

Also report: per-axis means with bootstrap 95% CI, harm rate (% rows with safety ∈ `{potentially_harmful, dangerous}`), as-good-as-reference rate, refusal rate, BERTScore-F1 and ROUGE-L in a supplementary table.

**Audit value-add:** the keyfact extractor's chain-of-thought is on HF at `audit/key_facts/<source>_keyfacts_reasoning.jsonl`. Use it to debug "why was this key_fact extracted?" — not for scoring.

### `open_ended_rubric` (healthbench_oss_eval, healthbench_consensus, healthbench_hard)

HealthBench's own evaluation formula:

1. For each row, you have the question (often multi-turn) and `rubrics: list[{criterion_id, points}]`. Resolve criterion text from `side_tables/healthbench_criteria.jsonl`.
2. Run a **single judge** (HealthBench's reference implementation uses GPT-4). The judge sees: full conversation + candidate final response + criterion text. Outputs `met: bool` for that criterion.
3. Score: `weighted_met = Σ(points × met) / Σ(max(points, 0))`. Negative-point criteria penalize harmful behaviors; the denominator is always positive by construction.

Use HealthBench's official judge implementation if possible (avoids re-deriving the prompt). Otherwise port the prompt from HealthBench's repo: <https://github.com/openai/simple-evals> / `healthbench_eval.py`.

## Caveats from the v0.2 build (read before reporting numbers)

1. **7 HealthBench oss_eval prompts are excluded** (2 also in `hard`, 3 in `consensus`). They couldn't be classified at v0.2 build time due to a known Qwen3 thinking-mode runaway pattern. A 397B cross-check confirms all 7 would have been classified `NONE` → zero in-scope loss. The disclosure is on the HF dataset card. **Effect on eval:** none — they're simply not in the loaded rows.

2. **MedQA-USMLE row set differs from v0.1.** v0.1 had 1,025 pre-filtered rows; v0.2 has 4,199 from a fresh refilter. Don't try to compare absolute MCQ accuracy across v0.1 and v0.2 — the row set is different.

3. **Cross-classifier evidence available.** `audit/classification_verdicts/oss_eval.qwen3_397b_v8.jsonl` carries Qwen3-397B verdicts on the same prompts (98.12% agreement with the 27B used at build). Useful for sanity-checking the eval's behavior on edge-case rows; not used for scoring.

4. **License mix.** Per-row `source.dataset` identifies license. AfriMed-QA + WHB are NC/SA — if you're going to publish scored outputs commercially, filter those configs.

## Concrete next steps (recommended order)

1. **Dataset loader migration.** Replace the v0.1 TSV table with an HF config table. Provide a `--revision` flag defaulting to `"v0.2"`. Sanity-check: `load_dataset("nmrenyi/mamabench", "kenya", revision="v0.2")` returns 312 rows.
2. **Audit `rescore_mcq.py` on v0.2 data.** Should be a 30-min adapter job; produces an end-to-end run on the 3 MCQ configs as a smoke test.
3. **Build `rescore_open_v2.py`** with the 3-judge ensemble per `open_ended_evaluation_research.md §7`. Don't delete `rescore_open.py`; keep it for v0.1 reproducibility.
4. **Build `rescore_rubric.py`** for the HealthBench-style configs.
5. **Create `configs/config-v0.2.0/`** with v0.2-appropriate `params.json` (judge ensemble, retrieval, generation params) and the deployed Swahili/English system prompts.
6. **Run the small initial matrix** (Gemma-no-RAG, Gemma-RAG, one frontier comparator) on one MCQ config + one open-ended config + one rubric config. Verify outputs look sane.
7. **Scale to the full matrix and full row sets.**
8. **Human ICC validation** (per the research doc): get a Kenyan clinician to rate ~50 open-ended rows on the same axes; report ICC vs the LLM jury before claiming the open-ended scores are calibrated.
