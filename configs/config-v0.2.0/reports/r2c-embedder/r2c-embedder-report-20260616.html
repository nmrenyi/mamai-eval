R2c Embedder Bake-Off — Comprehensive Report

2026-06-16 · config-v0.2.0 · branch feat/r2c-embedder-bakeoff-20260615 · EmbeddingGemma-300M vs deployed Gecko, on-device medical RAG (MAM-AI). Consolidates the per-phase docs in this folder (r2c-embedder/) + results in configs/config-v0.2.0/results/retrieval_eval/r2c-embedder/.

Bottom line. EmbeddingGemma-300M is a clear, deployable retrieval upgrade over Gecko (+12–13 pp retrieval; best deployable corpus coverage; ships on-device, latency-neutral). But it produces no-to-marginal end-to-end answer gains (kenya: none; healthbench: marginal) — and corpus coverage shows the corpus already contains the answer for ~89% of queries. The binding ceiling is the generator (gemma4-e4b), not the embedder or the corpus. → Adopt EmbeddingGemma as the retriever; the real next lever is generator RAG-grounding (G-RAG).

1. Objective & constraints

Close the Gecko-vs-top-tier retrieval gap with a better on-device embedder, and determine whether that converts to better answers. Hard constraints fixed during the run:

  • Runtime: LiteRT-only (the generator is .litertlm; no second runtime).
  • Hardware: low-/mid-end Android (Zanzibar) — latency/memory/storage are binding.
  • Language: English-primary; multilingual a useful bonus, not central.
  • Acceptance (pre-registered): ≥5 pp over the deployable baseline on the end-to-end metric, no penalty/refusal regression; 5 pp = the 1/√n noise floor at n≈312. Recall-primary.

2. Method — gated funnel

Deployability-first, then cheap→expensive, with the decisive test last (the lesson from the reranker line, which won offline but didn't convert):

P0 deployability gate → P1 corpus-coverage gate → P2 offline retrieval screen → P3 end-to-end value gate (kenya SAQ + healthbench rubric). Judges: Qwen3-32B + V2 rubric (retrieval/coverage); gpt-oss-120b (SAQ recall + HealthBench rubric) — the pinned v0.2 judges.

4. Synthesis — why the generator is the ceiling

Three findings only cohere one way:

  1. EmbeddingGemma is a clear retrieval upgrade (+12–13 pp; best deployable coverage; deployable).
  2. The corpus is mostly fine — it contains the answer for ~89% of kenya queries.
  3. Yet answers barely move, and RAG is net-negative on kenya with the deployed generator.
If better retrieval over a sufficient corpus still doesn't lift answers — and context actively hurts on kenya — the bottleneck is downstream: gemma4-e4b cannot convert retrieved context into better answers. Retrieval and corpus are not the binding constraints.

5. Recommendations

  1. Adopt EmbeddingGemma-300M as the on-device retriever. Strict, low-risk improvement on the retrieval axis (deployable, faster embed, multilingual headroom); best deployable option by a clear margin. Low downside even though it doesn't move today's answers.
  2. Open a generator RAG-grounding workstream (G-RAG) — prompt/format engineering and/or RAG-aware fine-tuning of gemma4-e4b so it uses (and isn't hurt by) injected context. This is where the end-to-end ceiling lives.
  3. R-corpus is a minor lever (~10% absent) — below G-RAG in priority.
  4. R2d (fine-tune the embedder) is not warranted — retrieval is already strong; the bottleneck moved downstream.

6. Execution notes & lessons (autonomous run)

  • Generator-baseline trap (twice-bitten lesson): the only sign-flip in the whole study was a baseline error — comparing to a retracted gemma3n number. Always confirm the generator before trusting an end-to-end figure.
  • Coverage method: 7 retrievers (gecko, EmbeddingGemma, bm25, medcpt, octen-8B, lateon-ColBERT, voyage-4-large) unified by normalized chunk-body hash (100% gecko/EG↔corpus alignment), 36,471 judged pairs — reusing the mamaretrieval pipeline on kenya queries.
  • Infra recovered autonomously: wiped cluster scratch (re-staged corpus); HF-gated EmbeddingGemma (license); expired cluster-side RunAI token (submitted via local RUNAI_LOCAL); 4 job-setup failures (read-only repo perms, missing python3, GPU preemption → added checkpointing to the 2.5 h coverage judge); H200→A100 pool move to dodge contention.
  • Statistical discipline: pre-registered 5 pp noise floor; the marginal healthbench edge sits within it.

7. Caveats

  • End-to-end sets are small/medium (kenya 312, healthbench 1209); marginal deltas are within noise.
  • Deployability measured on a flagship (SM8750); confirm on a true low-mid Zanzibar device before release (single-thread CPU is the proxy — deployability holds, latency will be higher).
  • bm25/medcpt/lateon are weak alone on kenya; they contribute little to the union beyond the dense retrievers.
